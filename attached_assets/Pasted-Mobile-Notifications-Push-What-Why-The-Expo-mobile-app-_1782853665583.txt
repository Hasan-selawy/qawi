Mobile Notifications & Push
What & Why
The Expo mobile app has a basic notifications screen that lists items but lacks read/unread management, preferences, and any push capability (expo-notifications is not installed). This task improves the mobile notification experience on top of the notification backend APIs and adds Expo push registration where feasible, keeping the existing bilingual EN/AR + RTL styling and not breaking existing routes.

Done looks like
The notifications screen shows read/unread state, supports mark-as-read and mark-all-read and archive, keeps pull-to-refresh, and has skeleton loading + empty states.
A user can manage notification preferences from the app (categories, mobile push on/off, preferred language, quiet hours where simple).
Where feasible, Expo push works: permission is requested only from a settings screen or a clear user action (never on load), the Expo push token is saved to the backend, the token is removed on logout, and permission-denied / emulator / unsupported cases degrade gracefully.
All notification UI respects the chosen language (EN/AR) and RTL, and no existing mobile routes are broken.
Out of scope
All backend endpoints, persistence, jobs, and actual push sending (handled by the notification backend task).
The web dashboard.
If Expo push cannot be completed safely in the current Expo setup, leave clear TODOs and keep the in-app notification experience fully working.
Steps
Upgrade the notifications screen to use the richer backend data — read/unread state, mark-one/mark-all read, archive — while preserving pull-to-refresh and the existing skeleton/empty-state styling and RTL/bilingual behavior.
Add a notification preferences screen (categories, mobile push toggle, preferred language, quiet hours where simple) backed by the preferences API, gated so push controls hide when the push feature flag is off.
Add Expo push support where feasible: install and configure notifications, request permission only from the preferences screen or an explicit action, and handle denied/emulator/unsupported gracefully.
Register the Expo push token with the backend on opt-in and remove it on logout, respecting the user's language and notification preferences.
Verify existing routes and the in-app feed still work whether or not push is enabled, and leave documented TODOs if any push step is not safely completable.
