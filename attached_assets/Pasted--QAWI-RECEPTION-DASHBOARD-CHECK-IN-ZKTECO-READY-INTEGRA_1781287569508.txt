* Search members by name, phone, or email

* See subscription warnings before check-in

* Update member contact info
* View today’s check-ins
* View expiring subscriptions
* View important member alerts

The Reception dashboard should help gyms replace:

* paper check-in sheets
* Excel member lists
* WhatsApp reminders

## POST /api/v1/reception/checkin/{memberId}

Backend logic:

1. Validate authenticated user is GYM_ADMIN or RECEPTIONIST.
2. Validate member belongs to same gym.
3. Check member subscription status.
4. If member already checked in today, do not duplicate unless existing attendance logic allows multiple.
5. Create Attendance record or return existing today’s record.
6. Calculate streak.
7. Return check-in result and warning if subscription is expiring or expired.

Request body optional:

notes

source = MANUAL_RECEPTION

checkinRecord

memberId

memberName

checkedInAt

streak

subscriptionStatus

daysUntilExpiry

warning

message

If subscription expired:

Return success but include warning:

EXPIRED

Do not block check-in unless the existing business logic already blocks expired members.

The receptionist should see a red warning and can renew immediately.

# ZKTECO BIOMETRIC INTEGRATION

## IMPORTANT

Do not build face recognition AI.

Do not build fingerprint matching.

ZKTeco devices handle fingerprint/face recognition on the device.

Qawi only needs to:

* register device serial numbers
* map device user IDs to Qawi members
* receive attendance scan events from the device
* create Qawi Attendance records

Actual biometric enrollment happens on the physical ZKTeco device.

# ZKTECO ADMS RECEIVER

ZKTeco devices may call the server without JWT auth.

So device receiver endpoints should not require normal user login.

But they must be safe:

* identify gym by device serial
* reject unknown device serial
* update device lastSeenAt
* rate-limit if possible
* never expose private data

Implement flexible parsing because devices may send form fields, query params, or plain text logs.

---

## GET /api/v1/zkteco/adms

Device ping endpoint.

No JWT auth.

Accept query params like:

SN

device_sn

serial

Update lastSeenAt if device is known.

Return plain text response.

Example response:

OK

or:

ATTLOGStamp=9999
OPERLOGStamp=9999
ATTPHOTOStamp=9999

Keep response simple because devices expect plain text.

---

## POST /api/v1/zkteco/adms

Device attendance push endpoint.

No JWT auth.

Accept possible fields:

SN

device_sn

serial

user_id

PIN

uid

timestamp

time

checktime

status

Also support raw text body lines if device sends attendance logs.

Backend logic:

1. Extract device serial.
2. Find BiometricDevice by serial.
3. If not found, return 404 or OK with warning log.
4. Update device lastSeenAt.
5. Extract device user ID.
6. Find BiometricEnrollment by deviceSerial + deviceUserId.
7. If no enrollment found, log unmatched scan but do not crash.
8. If enrollment found, get member.
9. Validate member belongs to device gym.
10. Create Attendance record using same service as manual check-in.
11. Avoid duplicate attendance for same member within a short window.
12. Return plain text OK.

Attendance source should be:

ZKTECO

If Attendance entity does not have source field, add safely if easy.
